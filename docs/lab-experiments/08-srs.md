# Experiment No: 8
## Title: Software Requirements Specification

### Aim
To study and prepare a Software Requirements Specification (SRS) document for the Campus Complaint & Maintenance Management System (CCMS).

### Objective
- To understand the purpose and structure of an SRS document.
- To identify functional and non-functional requirements of a software system.
- To document the requirements systematically following standard guidelines (e.g., IEEE 830).
- To create a comprehensive requirement foundation for the CCMS project.

### Problem Statement
The current process for managing maintenance complaints on campus is manual, paper-based, and inefficient. It leads to lost complaints, lack of accountability, and poor communication between the administration, maintenance staff, and the complainants (students and faculty). There is a critical need to formally specify the requirements for a proposed web-based automated system (CCMS) that will resolve these issues.

### Theory

**What is an SRS?**
A Software Requirements Specification (SRS) is a comprehensive description of the intended purpose and environment for software under development. The SRS fully describes what the software will do and how it will be expected to perform. It minimizes the time and effort required by developers to achieve desired goals and minimizes the development cost.

**IEEE 830 Standard**
The IEEE Recommended Practice for Software Requirements Specifications (IEEE Std 830-1998) is a widely recognized standard that describes the recommended approaches for the specification of software requirements. It outlines a structured format including Introduction, Overall Description, and Specific Requirements, ensuring all necessary aspects of the system are documented logically.

**Characteristics of a Good SRS**
A high-quality SRS should be:
1.  **Correct**: Every requirement stated is one that the software shall meet.
2.  **Unambiguous**: Every requirement has only one interpretation.
3.  **Complete**: Includes all significant requirements, whether relating to functionality, performance, design constraints, attributes, or external interfaces.
4.  **Consistent**: No subset of individual requirements described in it conflicts with each other.
5.  **Ranked for importance and/or stability**: Indicates the criticality of requirements.
6.  **Verifiable**: A requirement is verifiable if, and only if, there exists some finite cost-effective process with which a person or machine can check that the software product meets the requirement.
7.  **Modifiable**: Its structure and style are such that any changes to the requirements can be made easily, completely, and consistently.
8.  **Traceable**: The origin of each requirement is clear and if it facilitates the referencing of each requirement in future development or enhancement documentation.

### Procedure
1.  **Requirement Elicitation**: Analyze the problem statement and identify the needs of various stakeholders (Students, Faculty, Admin, Maintenance Staff).
2.  **Requirement Analysis**: Categorize the gathered needs into functional and non-functional requirements.
3.  **Documentation**: Draft the SRS document following the standard structure.
    - Define Purpose, Scope, and Overview in the Introduction.
    - Describe the Operating Environment and User Characteristics.
    - Detail every Functional Requirement clearly.
    - Specify Non-Functional Requirements (Performance, Security, etc.).
4.  **Review**: Verify the document against the characteristics of a good SRS.
